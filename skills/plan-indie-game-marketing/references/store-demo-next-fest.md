# Store page, demo, and Next Fest

## Coming-soon page gate

Put up the page once it can convert genuine interest, not merely because a page
can technically be approved. Before publishing, require:

- a settled primary genre and subgenre;
- a stable art direction;
- human-made capsule art that remains readable at small sizes;
- authentic gameplay footage showing the game quickly;
- varied, current screenshots that communicate play rather than menus alone;
- human-authored descriptions and calls to action;
- accurate tags, features, languages, platforms, and content disclosures; and
- a real destination for every public link.

Publishing earlier creates more opportunities to collect wishlists, but a weak
first impression can waste announcement traffic. If possible, coordinate the
page with a real announcement beat: a trailer, human-written press release,
targeted press outreach, notable showcase, or existing audience activation.
Do not publish the page quietly and assume it can be announced for the first
time later.

Use `audit-steam-store-page` for a detailed page review and
`review-game-trailer` for the video.

## Demo as a product and a beat

Define the demo's job: prove the core loop, build wishlists, collect broad
feedback, support festivals, or give creators a safe entry point. It should
reach the fun quickly and end after a satisfying payoff or meaningful desire to
continue.

Before public release, verify gameplay, onboarding, game feel, audio, settings,
input methods, performance, save behavior, failure/retry flow, and the path back
to the base game's wishlist action. Test with outsiders on clean machines.
Platform build review is not quality assurance.

On Steam, verify current rules for base-game page visibility, demo association,
separate demo pages, review timing, and the one-time wishlist notification.
Treat notification timing as a deliberate launch asset, not a button to press
automatically.

Keep the demo launch as its own beat by default. Prepare a human-written press
release and targeted pitch, a demo-specific trailer or strong clip, tested
install and wishlist paths, platform/community announcements, creator access,
and measurement before making it public.

## itch.io demo and browser build

Use itch.io when a low-friction browser or downloadable build helps with early
playtesting, game-jam or community discovery, press access, or players who are
not ready to install through Steam. Decide whether it is:

- a restricted or unlisted test shared with a bounded audience;
- a public itch.io demo supporting the Steam wishlist funnel; or
- a separately maintained release with its own audience and support burden.

Use itch.io's actual access controls and test the page while logged out. Do not
treat a draft page as a dependable distributed playtest. For an HTML5 build,
package the entry point and assets in the form itch.io currently requires, use
relative paths, and test the real embedded and fullscreen deployment rather
than only a local server.

The page still requires exact human-written public copy and human-made cover
art or screenshots. Give it an accurate build label, a working route to the
Steam wishlist or other primary action, support information, and any controls
or browser limitations the player needs to know.

A quiet restricted test does not spend the public demo-launch beat. A public,
announced itch.io demo does. Record what was available, to whom, and when; do
not later claim that a Steam demo is the first public playable version if that
is no longer true. An itch.io build also does not replace any public Steam demo
required for Steam Next Fest eligibility.

## Next Fest strategy

Steam currently permits one Next Fest appearance per title. Confirm current
eligibility and dates in Steamworks.

Default for a first-time or operationally inexperienced developer: choose the
later suitable Next Fest, release and test the demo beforehand, build an
existing wishlist base, then use the festival as a culmination. A compressed
announcement-demo-festival sequence can create momentum, but it depends on a
strong game, strong media, an established audience or major external beat, and
the ability to coordinate without shipping an untested demo. Label that route
as higher risk rather than as the default.

Build backward from press preview, trailer pulls, store/build review, and event
start. Add several business days for rejection and resubmission. Enter with a
stable demo, current first trailer, accurate tags, tested install flow, and a
plan for support and measurement during the event.
